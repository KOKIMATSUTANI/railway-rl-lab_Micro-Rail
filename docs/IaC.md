## Terraform-Based Automation for the GROSS Experiment Environment

The automated environment consists of:

- A dedicated VPC
- A public subnet
- An Internet Gateway
- A route table and subnet association
- A Security Group
- An IAM role and instance profile
- An EC2 instance
- An encrypted gp3 EBS volume
- Docker installation
- CloudWatch Agent installation and configuration
- Memory and filesystem usage metrics

## Division of Responsibilities

Terraform directly manages AWS resources, while EC2 `user_data` performs the operating-system-level bootstrap tasks.

| Component | Automation mechanism |
| --- | --- |
| VPC | Terraform resource |
| Subnet | Terraform resource |
| Internet Gateway | Terraform resource |
| Route table | Terraform resource |
| Security Group | Terraform resource |
| IAM role | Terraform resource |
| EC2 instance profile | Terraform resource |
| EC2 instance | Terraform resource |
| EBS capacity | EC2 `root_block_device` configuration |
| Docker installation | EC2 `user_data` |
| CloudWatch Agent installation | EC2 `user_data` |
| Memory and disk metric configuration | CloudWatch Agent configuration generated by Terraform |

Terraform does not itself install packages inside the instance. It supplies a startup script through EC2 user data, and cloud-init executes that script when the instance is first launched.

## Network Architecture

For an initial Dresden or Saxony experiment, a minimal architecture is sufficient:

```
Dedicated VPC
└── Public subnet in one Availability Zone
    └── EC2 instance
        ├── Public IPv4 address
        ├── No inbound Security Group rules
        ├── Outbound Internet access
        ├── Systems Manager access
        ├── Docker
        └── CloudWatch Agent
```

A private subnet with a NAT Gateway would provide stronger network isolation, but it would add infrastructure, operational complexity, and ongoing cost. For a single short-lived research instance, a public subnet with no inbound Security Group rules is a reasonable initial design.
